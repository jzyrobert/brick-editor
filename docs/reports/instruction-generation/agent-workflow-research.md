# Agent workflow for instructions from MPD

> Generated evaluation outputs referenced below are retained locally, outside
> this PR. See the [artifact policy](README.md#local-artifacts).

Investigation date: 1 October 2026. Repository baseline: `489443e`, heuristic v9. This is a tool and experiment design based on inspected code, primary documentation and the [continuing critic's actual findings](continuation-critic.md). It does not report the later three-round agent experiment or physical builder testing.

An agent should author an inspectable assembly programme, then examine its drawings. A final-pose parts split alone leaves the receiving interface, separate-object construction and handling problems that the deterministic critic has repeatedly identified. The useful division of work is deterministic source resolution, identity, replay and bounded geometry checks, with agent judgment over semantic groups, operation explanations and local diagram review.

## Evidence that changes the workflow

[Agrawala et al.](https://www.graphics.stanford.edu/papers/assembly_instructions/) combine planning and presentation, including part grouping, operation hierarchy, visibility and orientation. Their method accepts optional grouping and ordering constraints alongside final geometry. This supports letting an agent contribute explicit constraints rather than asking it to regenerate thousands of coordinates. Their paper also distinguishes action diagrams from pictures of the final structure: a visible final part is not necessarily an explained operation. This is design guidance for our workflow, not evidence that our arbitrary LEGO plans are buildable.

[Heiser et al.'s subsequent user study](https://graphics.stanford.edu/papers/assembly_instructions_study/) evaluates production, preference and comprehension in furniture assembly. It identifies clear ordered steps, relevant attachment views and action diagrams as useful, and lengthy text and occluded attachments as problems. The experiment demonstrates why visual review should accompany captions; its measured furniture results cannot be transferred to our LEGO models or substituted for builder trials.

The [LDraw file specification](https://www.ldraw.org/article/218.html) describes type-1 references and transformations and STEP boundaries. The [MPD extension](https://www.ldraw.org/article/47.html) separates embedded files and data blocks and makes referenced hierarchy significant. Resolve through the existing parser; do not regex-count every type-1 line as a loose part. Repeated submodel instances have distinct occurrence identities, file-local definitions can shadow library names, and part subfiles differ from buildable subassemblies. Preserve exact matrices, source records and embedded assets.

The [OMR specification](https://library.ldraw.org/documentation/official-model-repository-omr-standards/official-model-repository-omr-specification) asks authors to give separate objects such as vehicles and figures their own files and permits substitutions for unavailable parts. Source hierarchy is therefore useful semantic evidence, while not proving detachable stability or complete inventory. OMR is community-authored representation of official sets, distinct from LEGO's own manuals. Record each cached file's actual authors and licence header: current specification headers use CC BY 4.0, but the cached Shark file still declares CCAL 2.0. Do not silently rewrite an older source's licence.

[LPub3D](https://trevorsandy.github.io/lpub3d/) is a relevant open-source instruction editor: it provides submodel/callout presentation, prior-step fade/highlight, graphical part lists, PDF/image exports and headless/batch operation. Its [documented metacommands](https://trevorsandy.github.io/lpub3d/assets/docs/lpub3d/metacommands.html) offer a future interchange target. It is primarily a presentation/editor reference, not a substitute for assembly planning. This pilot should reuse Brick Editor's already pinned renderer and source data; no LPub3D binary was installed, benchmarked or integrated, and no GPL implementation or third-party connector data was copied.

Before implementing a wrapper, account for edit semantics: any structural `instructions.step.*` edit flattens the current workbench programme and removes derived joins. A camera edit clears derived supporting views, marks and checks. `instructions.installGenerated` requires the generation revision/fingerprint to match. An agent-edited manual plan must not retain stale generated CAD claims merely to pass installation. Full-plan validation or a new explicitly manual installation path is required for atomic programme edits.

## Recommended script contract

Provide one offline workbench entry point with a short help command and JSON files, avoiding shell-escaped giant arrays. These are proposed modes, not claims about an implemented CLI.

1. **Inspect:** input MPD/native path and output directory. Emit source hash, library locks, attribution, summary, stable alias-to-occurrence-ID map, source-group hierarchy, named part/colour lots, drawing ownership, exact transforms/bounds and strict contact coverage. Keep full detail in files; print only counts and filenames. Support filtering by source group, part or occurrence. Keep authored STEP comparison data in a separate optional file, so planners cannot accidentally use the reference as their answer.
2. **Baseline:** emit deterministic plan and editable native project plus provenance. Clearly distinguish root additions, detached builds and joins. Supply a compact table of step, action, additions, receiving candidates, warnings and current camera instead of the entire project in the prompt.
3. **Apply:** accept a bounded JSON proposal using aliases, existing operation IDs, ordered additions, named disjoint modules, build/join actions, notes and cameras. Resolve aliases centrally. Reject duplicate/missing IDs, partial drawing owners, overlapping modules, unfinished joins and receivers absent from the actual assembled destination. Preserve source models/assets and invalidate derived motion/visibility claims affected by structural edits. Save a new native file; never overwrite the source. Separate unsupported requested actions from accepted edits.
4. **Audit:** compare before/after exact source-model and occurrence poses, inventory ownership, exact-once introduction and programme replay. Report strict contacts separately from unverified candidates. Check each explicit ordering constraint against the state at the operation's start. Validate dimensions/budgets and emit named failures. A green audit certifies these invariants only.
5. **Review:** render explicit changed/risky operation IDs through the shared compositor, including adjacent operations, the actual prior receiving state, incoming module and source-facing alternate when needed. Emit small contact sheets plus individual images and a machine-readable capture manifest linking images to plan/source hashes. Support full HTML/PDF export within existing limits. Refuse an oversized whole export explicitly; selected review windows are not a complete booklet.

Use a repeatable output layout: `source.json`, `inspection.json`, `aliases.json`, `baseline.json`, `proposal.json`, `result.brickproj`, `audit.json`, `review/manifest.json`, `review/*.png`, `builder-notes.md`. Bound occurrences at the existing 5,000, operations at 2,000, captions at schema limits, render pixels/work at existing publication limits. Avoid unbounded all-pairs reporting. Neither a narrowed dossier nor a selected gallery may silently drop source leaves from the final plan.

Source-group and part filters make the workflow efficient. An agent should inspect one uncertain interface or module at a time, then render only the affected operations and their neighbours. Reuse expensive geometry only with an exact source/library/state/camera/compositor signature. Serialization and invariant checks should run on every proposal; expensive screenshots should follow meaningful plan changes.

## Efficient builder prompt shape

Keep the reusable prompt short and give each task concrete paths and a model-specific objective. Tool help and schemas belong in files rather than repeated in the prompt. A suitable starting prompt is:

> Create an editable hobbyist instruction draft for INPUT using WORKBENCH. Write all outputs under OUTPUT. Inspect the source dossier and deterministic baseline first; treat IDs as opaque aliases resolved by the tool. Preserve every source pose, reference, colour and drawing owner. Do not change repository code or fetch models.
>
> Identify the highest-impact confusing operations: mixed dependent additions, hidden destinations, wheels/figures/separate objects, enclosure order, mechanisms or flexible-item decisions. Plan small ordered operations and meaningful disjoint build→place candidates where supported. A vehicle positioned beside a building is a scene object, not an invented connector attachment. Explicitly record unsupported nested builds or physical flips instead of pretending the format represents them.
>
> For every uncertain operation name the incoming part/module, actual receiving candidate or competing candidates, uncertain fit/alignment/handling issue and builder decision needed. Use one concise action sentence; warnings do not replace a pictured procedure. Treat CAD clear/crossing/unknown only within the tool's stated scope. Never create a checked arrow, guessed flexible SKU/length, or physical-fit certificate.
>
> Apply the proposal and pass audit. Render changed risky operations with prior/current/next, incoming object and bare receiver when applicable. Open the actual images. Fix visibility and misleading sequence problems; re-audit and re-render affected states. Preserve useful existing wheel and workbench operations. Finish with result.brickproj, proposal, audit, capture manifest and brief notes identifying exact reviewed operation IDs, improvements and unresolved tasks. If a tool limitation prevents a repair, provide the concrete rejected request and evidence rather than a fabricated operation.

The critic receives artifacts and images separately, with no instruction to praise the agent's intended improvement. It should evaluate the operation as presented before reading the builder's rationale.

## Three-round experiment design

Use varied models, not only cases already helped by wheels: a small sample vehicle, a sample building with receiving/enclosure work, a compact official scene with figures/signs, and an articulated or Technic official set. The current local Car/House, 6450 and Shark or 8832 provide useful contrasting challenges; inspect each selected file before assignment. Distinct assigned models test transfer across part families; paired baseline-versus-agent review within each model is the meaningful comparison. Different models' raw scores do not rank the agents.

Freeze the source files, baseline, deterministic version, packs, capture settings, model assignments and critic rubric. Archive the exact prompt/tool revision before each round. Run three actual build→render→critic cycles; update tools and prompt from the preceding critic findings, then give those revisions back to builders. Record whether agents start fresh or revise earlier drafts and any inherited feedback. A cumulative refinement experiment is not an independent randomized test.

The critic should judge part selection, understandable action, receiver visibility, grouping/order, uncertainty specificity and diagram readability, and separately require source/coverage/programme invariants. Compare against the unedited baseline and previously completed round using exact occurrence/action IDs, not step numbers alone. When official references exist, compare a named fan-authored OMR step separately from a named LEGO PDF page. Builders should not be handed the comparator ordering unless the experiment explicitly tests manual-assisted editing.

Report score changes only for actual reviewed sequences. Track accepted edits, failures/rejections, operations reviewed, screenshots/publication pages, critical unresolved tasks, tool calls/time and expensive captures when logged. Prompt length and output bytes are measurable; do not fabricate token or cost savings. Explicitly retain unsupported strict-colour capture, oversized input/publication and mechanism/handling gaps. Three models or three reviews cannot establish broad corpus usability, deterministic generation, or physical builder success.
