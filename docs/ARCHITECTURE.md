# Architecture decisions

## ADR 001 — Authoritative document and occurrence identity

The domain core imports neither React nor three.js. A versioned project owns definitions, reference nodes, source records, layer assignments, groups, plans, bookmarks, mapping overrides and reserved rig/assets metadata. `Editor.project` returns a clone, so callers cannot bypass commands by mutating a returned object. Schema validators are generated at build time; imported projects cannot provide executable validators.

An occurrence ID is `JSON.stringify(nodeIdPath)`. Node IDs are unique **within their definition**, not globally. Copy-on-write copies definitions and local node IDs while changing the parent definition reference. Consequently the affected occurrence paths remain exactly the same, and layer memberships, groups, plans and overrides do not need identity remapping. Undo restores sharing. This is an intentional simplification of the spec's remapping sketch, with dedicated repeated-instance tests.

A command clones/stages the document, validates the complete result and commits once. Bounded structural patches store semantic JSON differences, not mesh objects or full render snapshots. Array changes currently replace their semantic arrays. History is capped at 100 entries and approximately 8 MiB of JSON text; oldest history is visibly flagged when discarded. A 500-entry session-only deduplication ledger rejects command ID reuse with changed content. Revisions advance monotonically through undo/redo. Replacement/import resets history after atomic staging; **undoing project replacement is not yet implemented**. The template UI exports the previous nonempty project first.

## ADR 002 — Starter subset, rendering and namespaces

Use a curated catalogue of 224 official physical parts (`scripts/catalog-parts.json`) and their official dependency closure, pinned as one versioned pack and loaded through a byte-exact bundle whose hash the manifest pins. A superseded lock is kept as a retired lock only when every file of its pack is byte-identical in the current pack (checked by `library:validate`); loading a project pinned to it re-pins it and records the previous lock in `metadata.previousLocks`, so no resolved definition changes silently. Each compile parses only the reachable closure of pinned files (from the build-time dependency graph), not the whole pack. A project-local `3001.dat` cannot inherit official purchasing identity. Geometry library and curated marketplace mapping pack are independently hashed and locked. Actual source headers and notices are retained. A connector pack (studs, side studs, jumper studs, anti-studs, door hinge pins and sockets, body occupancy boxes) is derived from this geometry at build time, hash-locked alongside it and recorded in each project's library lock; parts are `snapVerified` only when whole-part rules tie the derivation to their footprint and name (167 of 224; see [connectors](CONNECTORS.md)). Clips, finger hinges, Technic pins and solid collision compatibility remain unverified.

Parts outside the curated pack resolve from a second pack, the complete official library, pinned in the project lock as `library.full` and built from a hash-pinned official `complete.zip`. It is stored as content-addressed gzip chunks with an index that lists, per part, the chunks of its whole dependency closure and its build-time bounds, so a model's parts load in one planned batch and spatial features need no geometry. The index registers names synchronously for the document core (`installedSource`) and installs the bounds into the shared installed-bounds table; definitions are fetched, verified and cached per chunk and joined to a compile's closure next to the curated files. A definition that fails verification or is unavailable resolves as missing, never as partial geometry. The generated pack is committed rather than rebuilt in CI because `complete.zip` is replaced in place upstream on every LDraw release, so a pinned hash could not be fetched again later. See STATUS "Complete official library".

The same extractor and rules derive connectors and occupancy for every part of the complete pack at build time (worker threads), into a second hash-locked pack bound to that release: 256 content-addressed gzip shards, a part's shard chosen by a hash of its name, so no index is needed and a part's shard loads (verified, cached) with its geometry. `connectors.ts` answers from the curated pack for catalogue parts and from the registered shards otherwise, so snapping, clash tests, connectivity and health treat both alike; the CLI reads shards from disk synchronously. A new upstream archive becomes a new release through `library:update`: new complete and connector packs and locks, the previous release retired with the list of files whose bytes or closure changed, and projects re-pinned on load only when none of their complete-library parts changed.

The complete library's `!TEXMAP` images are a third pack bound to the same release (`textures-<release>`: unmodified PNGs addressed by SHA-256, a manifest pinned by `full-textures-lock.json` that also records which files and parts use which images). It is separate so adding it changed neither the complete pack's manifest nor any lock derived from it; it is not part of project locks because images only change how a part looks, never what it is, and a build that ships no image for a part draws its fallback geometry and says so. Texture-mapped subfile references (`0 !: 1 …`) are followed by the runtime loaders (`directReferences`) but are outside the complete pack's pinned closures, whose index predates them. Texture projection is computed with the geometry in the compile workers; images are decoded and shared on the main thread (see [rendering](RENDERING.md#textured-parts)).

The reference renderer owns one group per occurrence and shares compiled prototypes across occurrences with the same part/body colour. Source geometry and editable transforms never come from merged scene meshes. Prototype compilation uses an in-memory MPD and an explicit file map. This is necessary because the pinned loader rewrites `s/` references unless a mapping is supplied. The adapter rejects missing dependency attempts and empty official prototypes: the stock loader can otherwise swallow a subobject failure and return an empty group.

The colour configuration is read and hash-checked once, then the colour directives a compile references are compiled inside each isolated loader scope. Passing material objects into another loader instance is unsafe because edge and conditional-line caches belong to their originating loader. In-memory colour directives also allow uncached colour variants after the network goes offline.

Official parts share one compiled geometry across colours: the part compiles once in a sentinel main colour (a code no official part uses as a fixed colour), and each colour variant is a clone whose sentinel face, edge and conditional-line materials are replaced by the materials the loader builds for that colour on a one-triangle swatch. Materials are swapped only after both builds finish; they are never passed into another loader, whose edge and conditional-line caches would not know them. Fixed-colour sub-elements draw with the render context's shared palette materials for their code (see ADR 009). Singular (double-sided) contexts and custom parts still compile per colour. Each compile passes only the colour definitions its source references, not all LDConfig colours. Opaque non-reflected/non-sheared meshes instance; ordinary and conditional lines instance too (one draw per part/colour line set, the conditional-line shader applies the instance matrix to endpoints, direction and control points). Reference handles remain authoritative for picking and collision; transparent/reflected/sheared meshes use the reference path. Change-set-only traversal remains optimisation work. Cache retention is bounded and shared resources are disposed only once no retained prototype uses them. The renderer's budgets follow the resource profile (see [resource limits](RESOURCE-LIMITS.md#renderer-budgets)); it refuses over-budget workloads instead of dropping authored parts. These are declared budgets, not a performance claim.

Render space is a single π rotation about X. Occurrence transforms use full affine matrices. The renderer delegates internal custom-part compilation to pinned three.js; internal sheared references and broader BFC/material coverage are not yet certified. Ordinary lines and conditional lines use the loader's dedicated paths, not wireframe polygon edges. Diagnostic pink wireframe boxes represent unresolved references only. Catalogue thumbnails are build-time WebP renderings of the pinned geometry made by this renderer (`scripts/build-thumbnails.ts`), white bodies tinted in CSS to the held colour; they are previews, not replacements for model geometry. Every other placeable part of the complete library has a cell in a sprite-sheet atlas made by the same renderer (`scripts/build-part-thumbnails.ts`): one import renders a 16 × 16 grid of parts, each uniformly scaled into its cell with the curated framing, so the whole library renders in about two hours instead of days. Parts with fixed-colour geometry (prints, stickers, assemblies) are rendered twice, with a white and a black body; pixels that do not change are the print, and a tint-mask sheet keeps them out of the CSS tint. Sheets hold 64 cells, are content-addressed and pinned by an index whose hash is locked in the bundle (`part-thumbnails-lock.json`), so the browser verifies what it shows and caches it for offline use. They are committed like the complete pack; CI validates them but does not render. A transparent held colour shows any thumbnail as glass (curated glass is rendered opaque for this).

## ADR 003 — Source preservation and native packaging

LDraw records retain raw text, ordering and node anchors. Unchanged reference records retain original tokens; edited transforms use JavaScript double-precision serialization and normalize negative zero. Source custom geometry retains records and exports transformed coordinates. Unknown records remain in place. Root imported step boundaries are mapped into a native instruction plan; nested subassembly instruction expansion and ROTSTEP camera semantics are deferred.

Native ZIP stores `project.json`, `sources/project.mpd`, hash-named asset string files, a per-entry checksum manifest and notices. The project object remains authoritative; duplicated source and asset entries must agree on import. Legacy version-one bundles remain readable. Asset storage is not a claim that every image format or texture projection renders. Unknown project versions, graph cycles, non-finite transforms, unsafe paths and duplicate model names fail validation. Archive decompression is incremental and bounded. Lower physical-device budgets and full geometry decoded-memory accounting remain future work; decoded `!TEXMAP` image memory is budgeted per resource profile (see [rendering](RENDERING.md#textured-parts)).

Default MPD includes all authored occurrences and all retained embedded definitions. Filtered/scoped MPD flattens leaf placements in world coordinates; custom stateful metadata triggers an acknowledgement requirement. This implementation does not certify preservation of third-party metadata semantics after structural edits.

## ADR 004 — Offline inventory

The pack is an original small table of factual part/colour correspondences, not a copied bulk catalogue. Public source pages and verification date are recorded per pack. Each catalogue part identity was reviewed against its public BrickLink page title (evidence in `scripts/bricklink-review.json`); a palette colour counts as verified for a part only when BrickLink lists it among that item's known colours. Where an LDraw mould letter or renumbering differs (for example 3023b → 3023, 6141 → 4073), the mapping was accepted only after the title review and is annotated; parts without a matching item stay unmapped with a reason. Stock is not queried. Other mapped colour combinations are explicitly unknown until acknowledged. No automatic suffix stripping, nearest-RGB matching or marketplace login occurs. Beyond the catalogue, a second, derived table maps official parts to the BrickLink number their own LDraw file states (`!KEYWORDS BrickLink …`, CC BY 4.0 library metadata inside the pinned pack). It is pinned by hash inside the mapping pack, loaded only for inventories, never used for project-local definitions, and every lot it produces is reported as derived and needs an explicit acceptance (with colour existence unknown). Rebrickable's downloadable CSVs carry no BrickLink or LDraw identifiers, so they never map items on their own. A **reviewed** tier sits between the two: derived mappings a maintainer cross-checked with `scripts/review-mappings.ts` (the number the LDraw file states is the number Rebrickable uses for a part whose name agrees with the LDraw title, with no Rebrickable mould family); evidence per part is in `scripts/mapping-review.json` and the pack's `reviewed` section. It is reported as `reviewed`, never `verified`, and still needs acceptance. Ambiguous parts (the file names two numbers) carry their candidates.

**Parts-list decisions.** A user's choice for every occurrence of one part lives in `project.marketplace.partDecisions`, keyed `namespace:ref` (a project-local `3001.dat` never shares the official part's decision): an item number with its origin (`candidate`, `derived`, `reviewed`, `user`), `checked` (the user says they looked it up), `exclude`, and `acceptedColors` (uncertain colours the user accepted; never a colour known not to be made). Decisions are set by the undoable `inventory.override` command in its `{ part, decision }` form, validated in `src/inventory/decisions.ts` (BrickLink item shape only; typing a number verifies nothing), saved in native projects and hashed into the preview token. An occurrence override (`overrides`) still wins for its occurrence. `inventory.preview` returns `resolution` rows (part × colour: tier, what the list uses, candidates, colour existence, status, blocking codes) that the Export dialog's "Check your parts" list shows, needing attention first.

**Colour availability.** Which colours a part was really made in is a separate, hash-locked pack (`src/catalog/color-availability.json`, `scripts/build-color-availability.ts`), bound to the complete library release and loaded lazily. Verified entries are the BrickLink known colours of reviewed items; derived entries are the colours Rebrickable's pinned database snapshot records for the part (elements and set inventories), joined by the exact LDraw number or the BrickLink number a mapping states, never by stripping suffixes or merging moulds. Since 2026-09-30 the Rebrickable number an LDraw file states in its own keywords joins first (`scripts/part-joins.ts`, rule `k`): this is how printed variants (LDraw `p`, Rebrickable `pr`) get their own colours, and it corrects 48 exact-number joins the file contradicts. A hand-checked mould table (`scripts/mould-joins.json`, rule `m`) joins unjoined plain parts only where a Rebrickable mould (M) or alternate (A) relationship makes a candidate and a person accepted it. Colour identities join by the LEGO colour numbers LDConfig and BrickLink's colour guide both record (`scripts/color-joins.ts`), and Rebrickable by BrickLink colour names. The picker filters by it; inventories report each lot's `colorExistence` and block combinations the verified list excludes (`INVALID_PART_COLOR`). Only derived facts ship; the CSVs stay in the build cache, pinned by sha256.

Inventory walks semantic leaf occurrences and stops at physical part boundaries. User submodels expand, while primitive geometry inside a catalogue part does not become extra lots. Preview tokens bind the entire project hash, source scope, visibility, overrides, pack hash and options. This is deliberately stricter than revision-only validation. Locked layers remain readable. Unresolved/nonphysical/non-orderable occurrences block complete output; partial results carry XML plus a separate report. Authored-figure exclusion uses explicit `metadata.authoredFigureIds`, not filename heuristics.

Generic composite decomposition packs, ambiguous candidate resolution, purchased-stock allocation and all optional Wanted List pricing/preferences are not implemented. Such imports remain unresolved and cannot silently enter complete XML. Destination validation requires a separate human-authorized BrickLink session and has not been attempted.

## ADR 005 — Persistence, automation and deployment

LocalStorage saves a checked new envelope, then advances the head, retaining recoverable snapshots. Same-origin Web Locks serialize writers when supported, and stored revision comparisons refuse conflicts. Without Web Locks, an exclusive IndexedDB readwrite transaction serializes checksum/read/publish operations; project bytes remain in LocalStorage. A timeout guard prevents late publication after lock expiry. If neither coordination mechanism is available, writes fail with a backup/retry UI. Storage events notify other tabs without replacing their drafts; users can fork or back up before reloading the saved revision. No automatic project-data migration to IndexedDB occurs. Serial autosave uses a 750 ms debounce and three-second scheduling target; completion latency still depends on storage and browser scheduling.

Browser automation is opt-in (`?automation=1`) and shares the command/inventory services with the UI and CLI. Workers handle LDraw parsing and rectangular fills; jobs expose running/success/failure/cancellation. Native decompression remains on the main thread with bounded streaming. Image capture uses a fixed revision and offscreen target, restores renderer state in `finally`, validates dimensions and returns a manifest. GPU pixels are not promised identical across platforms. Fast/Balanced/Photo apply distinct edge, shadow, tone and pixel-ratio policies; bounded overrides are independent. Capture restores interactive settings and includes the actual light rig, quality controls, clipping planes and device limits in its manifest.

The production bundle is static and works under a Vite base path. No third-party runtime fonts, scripts, model uploads, secrets or rendering service are required. The CLI's temporary localhost server is a local development/testing adapter.

## ADR 006 — Milestone order and scope boundary

The user explicitly reprioritized Play while continuing the remaining roadmap and requested parallel agents plus an independent mobile UX loop. This supersedes the previous implementation order without declaring unfinished P0 gates passed. Rapier 0.21.0 is now lazy-loaded for a kinematic capsule over actual triangle surfaces. First-person exploration has no body; the original procedural third-person figure uses only declared rigid joints. Play state never implicitly edits the project. Authored hinges and planar kinematic vehicles are a separate rig session; applying a pose is revision-checked and undoable. Dynamic suspension, advanced assembly planning, path tracing and collaboration are not claimed implemented. PDF publishing uses lazy-loaded pdf-lib with sequential bounded captures.

The scaffold's vulnerable dependency versions were replaced with exact patched pins and a regenerated lockfile. See the dependency audit and final verification report. The three.js r174 loader is deliberately pinned behind its adapter; the matching type package has a parse signature mismatch, isolated with one documented structural cast at the adapter boundary.

## ADR 007 — Explicit offline snapshots and links

Offline installation is a user action, caching one versioned app, lazy feature chunks and pinned starter library. The complete LDraw pack (86 MB) and its thumbnail sheets are excluded from that snapshot; the app caches each verified chunk or sheet it loads in its own Cache Storage cache, so parts a model has used (and thumbnails once seen) stay available offline. Update activation is explicit and prior snapshots are retained. Cached static responses ignore `Vary` after same-origin scope checking, since module requests can carry different Origin headers from precache requests. No authenticated/remote resources are cached. This policy is verified by a full offline reload and feature loading, not just a disconnected current tab.

Share links contain bounded compressed MPD, a library lock and checksum. They exclude local history and native-only editor metadata. Imported links preview as temporary projects before an explicit open; nonempty current builds are backed up first. A checksum detects accidental corruption, not authorship.

Play moving collision derives separate triangle meshes for authored rigid groups, leaving the static snapshot free of duplicate rest-pose surfaces. Both rendering and collision use the same fixed-tick kinematic pose. Swept surface displacement bounds conservatively block motion near the walking capsule; no riding, pushing or vehicle/world response is implied. Instruction metadata is an optional parallel array validated to match step count, with reorder/split/merge/filter operations updating both arrays atomically.

On WebGL loss, capture waits and owned shader-completion polling abort. The pinned Three renderer restores its internal GPU caches from retained scene resources; the adapter resets render target/viewport and invalidates the view. Shader polling uses the pinned renderer material/program properties and is bounded to 30 seconds. Regression coverage must be rerun when upgrading Three.

Editor mode lifecycle effects are separate from instruction-plan preview effects. Document replacement cancels an old Play session synchronously; delayed React plan rendering must not cancel a new API session entered immediately after an import. A cached import/edit/undo/Play regression covers that ordering.

## ADR 008 — Motors, optional dynamics and derived doors

The dynamic slice reuses the pinned, lazily loaded Rapier 0.21.0 and adds no dependency. Dynamic rigs live in a second Rapier world with gravity. That world steps exactly once per fixed tick, because the walking world is also stepped for query refreshes. The explorer is a kinematic capsule in the dynamic world, and dynamic bodies are mirrored into the walking world as obstacles; walking into a loose body applies a bounded impulse. Bodies are created with identity rotation at their group origin, so every joint uses world-aligned anchors and axes. The group frame is `bodyPose ∘ restFrame`. Authored groups are the rigid unit. Moving groups use per-member convex proxies that can only shrink under point reduction, and anchored groups keep exact trimeshes. Dynamic vehicles use Rapier's ray-cast wheels, with the axle flipped when needed so positive throttle drives along the authored forward (−Z).

Kinematic motors run through the same swept actor-clearance path as joint targets. An idle fast path skips pose and sweep work, and the resulting collider updates, for rigs that cannot move this tick. KinematicSession keeps only the source revision instead of cloning the whole project, and play sources can share one occurrence index. This keeps many derived rigs linear in large builds.

Official LDraw doors are hinged by session-only derived rigs from a pinned, geometry-derived table (`src/play/door-parts.json`, regenerated by `scripts/build-door-table.ts` and re-derived in tests for pack parts). They are never written to the project. The free swing direction is decided once at entry by sweeping an inset convex proxy of the leaf against the Play world. Static posed export writes transforms into a private copy through the same copy-on-write helpers as commands, so rest-pose export stays the default.

## ADR 009 — Off-main-thread part compilation and the geometry cache

Opening a few-hundred-part template froze the page for 10–17 s on the test VM. Profiling showed 95% of it in one function: the pinned LDrawLoader's `smoothNormals()` restarted a `for…in` over a plain object after every deletion, which is quadratic in a part's half-edge count (the 32×32 baseplate alone). The loader is therefore vendored (`src/render/vendor/LDrawLoader.js`, three r174, MIT) with that loop replaced by a live `Map` iterator: the same entries in the same insertion order, so output is bit-identical to upstream (a unit test compares both loaders attribute by attribute). Other patches must be marked "Brick Editor patch" in the file.

Official part geometry (the sentinel-colour shared base of each part and render context) compiles in a small worker pool (`src/workers/part-compile.worker.ts`, `src/render/part-compiler.ts`; two to four workers on desktops, at most two on phones, leaving a core for the page and the GPU process). A worker parses the same self-contained compile source the main thread used to parse, repairs normals, indexes the triangles exactly as the renderer does (`geometry-index.ts`, so records are stored indexed and colour variants still share one geometry), and returns a **part record** (`src/render/part-record.ts`): one `ArrayBuffer` with a JSON header (object tree, transforms, names, geometry groups, and the colour code and kind of every material slot) followed by the attribute arrays. The buffer is transferred, not copied, and the main thread wraps views of it in Three objects. Materials never cross threads: each slot is bound to the render context's palette material for that code (the same loader-built swatch materials colour variants already used), so rebuilt parts draw exactly as a main-thread compile would, and fixed-colour sub-elements now share materials across parts, which `tuneMaterials()` tunes once each. Parts whose closure defines file-local colours, direct colours or unknown codes cannot be described by code; the worker declines them and the main thread compiles them as before. Custom (project) parts, singular render contexts and raw primitives also stay on the main thread. If workers cannot start (or crash), every part falls back to the main thread.

Records are stored in a persistent **geometry cache** (`src/render/geometry-cache.ts`, IndexedDB `brick-editor-geometry`, shared by tabs of one origin). The key names everything the geometry depends on: compiler version (`PART_COMPILER_VERSION`, which includes the three revision and must be bumped with any loader, BFC-normalization, normal-repair, indexing or record-layout change; `bpc4` added `!TEXMAP` objects, their `uv` attribute and `userData.texmap` tags), the curated and complete library manifest hashes, the render-context fingerprint (SHA-256 of the BFC/colour context) and the part name. Each entry stores its SHA-256; a read that does not match is deleted and recompiled. Entry metadata lives apart from the bytes, so the LRU index loads without reading geometry. The cache is bounded (128 MB desktop, 48 MB phone profile), evicts least-recently-used entries, retries once after a quota error by halving itself, and otherwise degrades silently to compiling. Being a derived cache it is not part of offline snapshots or project locks; offline reload works because the worker script is precached with the app.

Main-thread work that remains (render-context and variant analysis, palette swatch parses, rebuilding records, creating occurrence handles) runs through one scheduler that ends the task whenever about 12 ms have been used (`src/render/scheduling.ts`: `scheduler.yield()` or a MessageChannel message, never a clamped timer). A newly opened model is drawn progressively: prototypes are requested most-used variant first, and what has compiled is placed and batched after 150 ms, then again whenever the drawn set would double (else after a second), spaced so partial redraws cost at most a fifth of the load, and only once a WebGL fence shows the GPU finished the previous partial frame (software rasterisers can fall seconds behind, and the next synchronous call — a shader link — would block the page). Parts shown while loading never exceed the profile's triangle budgets; a model refused at the end is taken down again. Edits of the open model still swap in all at once. A small progress bar in the status toast reports compiled variants; it lives outside React state, so its updates do not re-render the workspace. Before any part has compiled, a newly opened model (template, import or recovery) is drawn as a loading skeleton: one instanced draw of a translucent box per occurrence from the build-time part bounds (`src/render/load-skeleton.ts`), after 150 ms, or at once for models of 4,000 parts or more. Parts are requested and revealed in instruction-step order, else from the ground up, and each flush hides the boxes of the parts it draws. See [PERFORMANCE-MINEBENCH.md](PERFORMANCE-MINEBENCH.md#6-loading-skeleton).

At page load the recovered project is read, hash-checked, parsed, validated and re-pinned in a worker (`src/workers/project-restore.worker.ts` via `src/persistence/restore.ts`); the main thread parses the verified JSON once and calls `Editor.replace(project, { trusted: true })`, which skips the second validation and deep copy (a shallow copy keeps the caller's object unchanged). Legacy localStorage snapshots, a missing IndexedDB copy or a worker that cannot start fall back to the validating main-thread path.

**Clearing saved builds.** The last item of the Project menu, **Clear saved builds…**, sits under a quiet rule. Its confirmation (an `alertdialog`, focus on Cancel, Escape cancels) counts what it will delete (“2 saved projects and 1 checkpoint”, `countSavedBuilds` in `src/persistence/clear-saved.ts`), says it can't be undone and suggests a native backup first. Confirming drops the pending autosave and, inside the save queue, clears the `projects` store of IndexedDB `brick-editor-projects` (every project and its autosave snapshots), the legacy `brick-editor:<id>:…` localStorage snapshots and the `brick-editor-current` pointer (`BrowserProjects.clearAll`), and every checkpoint (`brick-editor-checkpoints`). It then opens a blank canvas that is not autosaved until it changes, so a reload recovers nothing. The geometry cache (`brick-editor-geometry`), the complete-library chunks, part thumbnails, cached official sets and preferences are other stores and stay warm. Other tabs get the usual change notification and keep their drafts.

The rest of the large-model load path follows the same rule (30 September 2026). LDraw imports are validated (schema and source) in the import worker, and the automation/UI import adopts the worker's result as trusted. Autosave runs in a persistent save worker (`src/workers/project-save.worker.ts`, `saveSnapshot` in `browser-projects.ts`): validation, JSON, hashing, verifying the stored copy it replaces and the IndexedDB publish, under the same cross-tab Web Lock the page would take; the page only posts the project. A save that needs the page's localStorage (a legacy copy to migrate), or a browser without workers or Web Locks, runs on the main thread as before, and nothing is written before that hand-back. The UI's commit subscriber reads the editor's installed document (`Editor.snapshot`) instead of deep-copying it: the editor never mutates a document once installed (commands copy it), and every consumer of that snapshot treats it as immutable. Complete-library change notifications are coalesced (400 ms quiet, at most 3 s late) before the workspace re-derives every occurrence. Occurrence handles are records rather than cloned trees (see [rendering](RENDERING.md#frame-cost-on-large-models)), and a model's first full frame is prepared in separate tasks (classification, fill, shader warm-up) while frames are held.

**Complete-library updates.** A project pinned to a superseded complete release is re-pinned on load only when none of its parts changed (`adoptCurrentLocks`). Otherwise it keeps the pin and those parts stay unresolved rather than silently changing, and Project shows **Update to the latest parts library**: `libraryUpdateStatus` (`src/catalog/library-update.ts`) lists the project's parts in the retired lock's `affected` list (or every part outside the curated pack when the release is unknown or `affected` is null), and the undoable `library.update` command re-pins after the UI/API saves a checkpoint, appending `{ full, reason: "user-update", textures, changed }` (`textures`: the `!TEXMAP` texture pack lock bound to the new release, which projects follow with their complete-library pin rather than pinning separately) to `metadata.previousLocks`.
