# Refine a deterministic instruction draft

Use with INPUT, WORKSPACE and a concrete review objective. Read
[HYBRID-INSTRUCTIONS.md](../docs/HYBRID-INSTRUCTIONS.md) for commands and artifacts.

---

Improve the latest deterministic instruction draft for hobbyist builders. Run
the hybrid tool's `prepare`, read its pinned baseline, compact inspection and
proposal, and keep all artifacts in WORKSPACE. Work from that baseline proposal;
do not replace it with an earlier manual draft. Do not edit shared code, fetch
models or change the input.

Inspect actual baseline pictures before choosing edits. Prioritize a few
concrete failing windows: mixed dependent additions, hidden receiving features,
missing build/place actions, closure before interior access, or unexplained
loose foundations. Record the baseline operation keys and affected aliases.
Query only relevant parts/groups through workbench `inspect`. Preserve useful
baseline wheel/joint procedures, their membership and destinations. Retain
unchanged operation keys so the comparison remains traceable.

Keep every occurrence, reference, colour, namespace, raw pose and whole drawing
owner. Retain the tool's support, host and access prerequisites and actual
destination-workbench availability. Use purposeful small additions; group only
independent actions whose receivers already exist. Introduce each part once.
Build a child separately, place it into its parent, then finish/place the parent.
Distinguish scene placement from attachment. Source hierarchy and STEP can
organize a candidate procedure; they do not establish detachable stability.

Use a complete alias proposal, making the smallest justified changes to notes,
cameras, ordering or modules. `before` is a pair of part aliases, not operation
keys. Name the incoming object, actual receiver and visible landmark in each
difficult action. Explain specific loose support, alignment or handling decisions.
Do not substitute blanket warnings for a pictured procedure. Use the existing
CameraSpec reference; a camera rotation is not a physical turn. Do not invent
fit/stability testing, checked arrows, flexible-item identity or a CAD route.
Changed procedures keep fresh conservative unknown outcomes unless the tool
has applicable current evidence; never restore stale generation claims yourself.

Run `refine` with the pinned baseline hash. Read the exact delta and both audits.
Resolve refusals without deleting prerequisites or source parts. Keep the plan
within publication limits when this can be done honestly; report an oversized
refusal. Render changed/risky keys with prior/current/next and open the actual
images. Inspect bare receivers, incoming objects, completed interfaces and wider
context. Reveal actual socket mouths, clips, pins and printed fronts rather than
marking their containing body. Notes must remain understandable in live views
without publication letter markers. Re-audit and re-render after repairs.

Deliver proposal, native result, audits/delta, source notices, capture manifests
and brief `builder-notes.md`: baseline/refined key mapping, concrete verified
changes, reviewed image scope, remaining decisions and rejected requests.
Give the latest baseline and refined pictures to an independent critic before
your rationale. Selected windows are selected evidence; passing invariants does
not establish usability or physical assembly. Report the critic's comparison
without assuming an improved score. Check real phone/publication outputs when
requested, and record any pending or refused checks.
